## What's New in v0.11.1

A hardening release. There is nothing new to learn: things that used to go wrong silently now either work or tell you why they did not.

### Your own `xclip` / `wl-paste` is never overwritten

If `~/.local/bin/xclip` (or `wl-paste`, `wl-copy`) on the remote was something you put there yourself, older versions replaced it with the cc-clip shim and it was gone. `cc-clip connect` now refuses and names the file. To let cc-clip take the path anyway, opt in:

```bash
cc-clip connect <host> --adopt-foreign-shim
```

Your program is moved to `<path>.cc-clip-real`, the shim falls back to it, and later reinstalls (`--force`, a port change) keep using it. If any step of the install fails, everything it moved is put back.

### Codex paste: private display, and it survives other deploys

- The virtual X display that serves Codex now requires an authorization cookie, so other users on a shared host cannot read your clipboard through it. Existing Xvfb instances are restarted once on the next `connect --codex`.
- `cc-clip connect <host> --claude` on a host that also runs Codex no longer leaves Ctrl+V dead in Codex.
- The bridge is now recognized on BusyBox-based remotes, where `ps -p` does not exist.

### Notifications that were silently lost now arrive

Codex and opencode notifications, and any notification on a non-default `--port`, now reach your machine. `cc-clip doctor` no longer reports an older managed Claude hook as "wired for a DIFFERENT port" when the port is correct.

### Credentials on the remote

The token, notification nonce and session ID are created private (0600 in a 0700 directory) from the first byte, and are replaced by rename rather than rewritten in place, so a process that opened an old copy cannot read the new one.

## Other Improvements

- `cc-clip setup` edits land in the right SSH config scope: a `Host` block now ends at a following `Match`, tab-separated directives are recognized, and `setup user@host` writes a `Host host` block that ssh actually applies. An `Include` or an earlier conflicting `ControlMaster` / `ControlPath` is reported as a warning with the `ssh -G` command to check.
- Clipboards that offer only JPEG now paste instead of failing after being advertised as an image.
- `cc-clip serve --rotate-token` that loses the port to a running daemon no longer rotates that daemon's token.
- The launchd service keeps a custom `--port` across `cc-clip update`.
- On the remote, fetched images are saved in a per-user directory; a directory or symlink another account created under the shared `/tmp` fallback is refused instead of reused.
- `xclip` writes with a file argument pass through to the real binary unchanged.
- Windows hotkey: config, focus capture, tray window handle and a config race are fixed.

## Behaviour Changes to Know

- **`cc-clip setup` now rewrites a conflicting `ControlMaster` / `ControlPath`** in the target `Host` block (previously it only added missing lines). It writes `~/.ssh/config.cc-clip-backup` first and reports `updated (was X)`.
- **Installing over a program cc-clip did not write now stops** unless you pass `--adopt-foreign-shim` (see above).
- **Codex hosts restart Xvfb once** on the next `connect --codex`, to pick up the authorization cookie. Open Codex sessions get Ctrl+V back after their shell re-reads the display settings (open a new shell or tab).

## Upgrade

**Local machine first, then each remote host.**

```bash
# macOS / Linux, existing install
cc-clip update

# macOS / Linux, fresh install
curl -fsSL https://raw.githubusercontent.com/ShunmeiCho/cc-clip/main/scripts/install.sh | bash
```

```powershell
# Windows, install or upgrade
irm https://raw.githubusercontent.com/ShunmeiCho/cc-clip/main/scripts/install.ps1 | iex
```

Then, for every remote host:

```bash
cc-clip connect <host> --force
```

## Not in This Release

- **Claude Code on Wayland-only remotes.** Current Claude Code probes the clipboard with `wl-paste -l`, which the shim does not intercept yet, so paste fails on a remote with no working `xclip`. The fix is in review (#151).
- **`cc-clip uninstall` does not move an adopted program back** from `<path>.cc-clip-real`; a fix is in progress.
- **Windows changes are not verified on real hardware**, and neither are the opencode, Antigravity and Cursor notification paths. Reports welcome.
- **Persistent per-host SSH tunnels** (#108) are being worked on by a contributor; **notification icon/sound settings** (#92) remain open.
