## What's New in v0.13.0

### Keep the tunnel up on its own (experimental)

Until now, whichever `ssh <host>` connected first owned the paste tunnel. If that session closed, or its client disappeared on a flaky network while the remote side kept the port, paste stopped working until you found and ended it.

`cc-clip tunnel run <host>` keeps the tunnel on a private SSH connection instead. It holds exactly one loopback reverse forward, checks the daemon through it, and reconnects with backoff when the connection drops. (#108, #165, @paigeman)

```bash
cc-clip connect <host> --force   # once: deploys the helper the supervisor probes
cc-clip tunnel run <host>        # foreground; Ctrl-C stops it
```

It is opt-in and manual:

- It changes nothing in your SSH config, installs no service and enables nothing by itself. The existing `RemoteForward` setup stays the default.
- It reports distinct states: healthy, reconnecting, port conflict, remote token invalid, identity helper missing, and others.
  - When the remote token is stale, it keeps the connection up and tells you to run `cc-clip connect <host> --token-only`.
  - After repeated failures it stops, until you run it again with `--reset`.
- An interactive `ssh <host>` still asks for the same port. If it got there first, the supervisor reports `port-conflict` and waits for the port to be free.
- Hosts set up with `--use-remote-bin` are not supported yet.
- While it runs, its checks keep the token from expiring.

### When a tunnel is held but silent, cc-clip shows you which session holds it

If the port is held on the remote but no daemon answers, `cc-clip connect` and `cc-clip doctor --host` now list your own `sshd` sessions on the remote with their start times. They mark the session the check itself ran under, and print a fix that needs no root:

```bash
ssh -o ClearAllForwardings=yes <host> 'kill <PID>'
```

The previous advice (`lsof`, `sudo ss`) usually could not be followed as a normal user. The troubleshooting guide now covers the "connects, then hangs" symptom and `ClientAliveInterval` as prevention. (#173, #176)

### Slow links no longer break `connect`

The release download for the remote used to give up after a fixed 30 seconds, so a 3.4 MB archive failed below about 115 KB/s. It now fails only when the transfer stalls (under 1 KB/s for 30 seconds), within the same 5-minute budget `cc-clip update` uses. When `connect` falls back to cross-compiling, it now names the source directory and commit it builds from. (#174, #177)

## Other Improvements

- `cc-clip doctor --host` no longer mixes the remote shell's job-control warnings into the `path-order` result. (#175, #178)
- The README, the Chinese and Japanese READMEs, and `docs/commands.md` document `cc-clip tunnel run`. (#180)

## Behaviour Changes to Know

- **`cc-clip serve` creates `~/.cache/cc-clip/instance-id`** (mode 0600) on first start, so the managed tunnel can tell which daemon it reached. This file is new in this release. If the file cannot be read or created, the daemon still starts and only the new identity check is unavailable.
- **The daemon has a new authenticated endpoint, `/tunnel/identity`.** It uses the same token and User-Agent checks as the clipboard endpoints and answers 401 without them.
- **`connect` can now wait up to 5 minutes** for the remote binary on a slow link, where it used to fail at 30 seconds.

## Upgrade

**Local machine first, then each remote host.**

```bash
# macOS / Linux, existing install (v0.12.3 or later falls back if the GitHub API is rate-limited)
cc-clip update

# On an older version behind a rate-limited network, name the version:
cc-clip update --to v0.13.0

# macOS / Linux, fresh install
curl -fsSL https://raw.githubusercontent.com/ShunmeiCho/cc-clip/main/scripts/install.sh | bash
```

```powershell
# Windows, install or upgrade
irm https://raw.githubusercontent.com/ShunmeiCho/cc-clip/main/scripts/install.ps1 | iex
```

Then, for every remote host (required before `cc-clip tunnel run` can reach it):

```bash
cc-clip connect <host> --force
```

## Not in This Release

- **Managed tunnels as a service** (`cc-clip tunnel enable`, a LaunchAgent, migrating hosts off `RemoteForward`) are later phases of #108. They wait for real-host experience with `tunnel run`.
- **`--use-remote-bin` hosts** cannot use the managed tunnel yet.
- **Grok Build notifications** wait for a confirmed real-host paste (#147).
