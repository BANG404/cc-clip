## What's New in v0.13.1

Fixes from the first real use of v0.13.0 and from review: `connect --codex` stops warning about a notify line that works, `tunnel run` says where it must run, and `doctor` and the Windows installer each lose a failure case.

### `connect --codex` no longer warns about a working cc-clip notify line

If `~/.codex/config.toml` already had a top-level `notify` line that runs cc-clip (added by hand or by an older version), every `cc-clip connect <host> --codex` printed

```text
warning: Codex notify setup failed: ... existing top-level notify setting found ... refusing to inject duplicate
```

while `cc-clip doctor --host <host>` reported the same file as working. Both commands now apply one rule. The line is left untouched and counts as wired when it is exactly one of

```text
[env VAR=VALUE ...] cc-clip notify [--port N | --port=N] --from-codex
[env VAR=VALUE ...] cc-clip plugin run codex-notify
```

and posts to the port you connect with. `connect` then prints a note instead of a warning. A line that targets another port, or mentions cc-clip in any other shape (a shell wrapper, extra arguments), fails with a message that says why and how to fix it: remove the line and re-run `cc-clip connect <host> --codex`, which writes the managed block. A `notify` setting that does not mention cc-clip is still respected and never overwritten. `doctor` also reads a `'notify'` key written with single quotes. (#187)

### `tunnel run` says it belongs on the local machine

Run on the remote host, the experimental `cc-clip tunnel run` stopped with `local daemon instance does not match persisted tunnel spec` and no hint. On the remote, `127.0.0.1:<port>` is the forward back to your local daemon, so the instance that answers can never match. The message now names that cause and the fix, and the README, `docs/commands.md` and the help text say to run it on the machine where you copy images.

The README and `docs/commands.md` also explain `port-conflict`: any other SSH connection to the host that applies the `RemoteForward` from `~/.ssh/config`, such as a terminal tool's background connection, takes the port first. `tunnel run` never takes over a port that another connection holds. To try it, end that connection and comment out `RemoteForward` for the host. (#182, #183)

## Other Improvements

- **`doctor --host` no longer reuses an SSH master.** Its checks set `ClearAllForwardings` but could still ride an existing `ControlMaster` connection that owns the forward, and then label its own session "not the holder". The checks now pass `ControlMaster=no` and `ControlPath=none`, except on Windows, where OpenSSH has no master to reuse. The stale-session guidance also no longer calls a session stale just because it has no client on this machine: it may be open from another computer. (#186)
- **`install.ps1` works behind a rate-limited IP.** Like `install.sh` and `cc-clip update` in v0.12.3, the Windows installer now falls back to the `releases/latest` redirect when the GitHub API returns 403. If both fail, the error names the 60 requests/hour per IP limit and how to pin a version with `$env:CC_CLIP_VERSION`. (#185)
- **`connect` cross-compiles honestly from a tree with new files.** An untracked `.go` file, `go.mod` or `go.sum` is compiled into the binary, so it now marks the source tree as modified in the cross-compile message; untracked notes still do not. (#186)
- **Release notes corrected.** The v0.12.3 page shows the `CC_CLIP_VERSION` pin for Windows. The v0.13.0 page says `/tunnel/identity` answers 403 for a missing or unrecognized User-Agent, and that a `cc-clip serve` you started yourself must be restarted after updating. (#184)
- **Managed tunnel design document** in `docs/plans/` for the coming persistent-tunnel work (#179, @paigeman).

## Upgrade

```bash
# macOS / Linux, existing install (0.6.2+)
cc-clip update

# macOS / Linux, fresh install
curl -fsSL https://raw.githubusercontent.com/ShunmeiCho/cc-clip/main/scripts/install.sh | bash
```

```powershell
# Windows, install or upgrade. If the installer stops with a GitHub API
# rate-limit error, pin the version first:
$env:CC_CLIP_VERSION = "v0.13.1"
irm https://raw.githubusercontent.com/ShunmeiCho/cc-clip/main/scripts/install.ps1 | iex
```

Then refresh each remote host so it runs the new binary:

```bash
cc-clip connect <host> --force
```

If you use Codex and `connect` now reports your existing notify line as unconfirmed or on another port, remove that line from `~/.codex/config.toml` on the remote and re-run `cc-clip connect <host> --codex`.

## Not in This Release

- **Persistent per-host SSH tunnels, Phase 1b** (#108): the background service, `tunnel enable/status/disable` and the SSH config migration are planned in two follow-up PRs. `tunnel run` stays experimental and foreground-only.
- **Grok Build notifications** wait for a confirmed real-host paste (#147).
- **Windows**: the `install.ps1` fallback and doctor's Windows SSH arguments are checked by tests, not run on a Windows machine.
